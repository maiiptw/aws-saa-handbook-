# Module 4: Databases & Caching Layer

หากเปรียบระบบคอมพิวเตอร์เป็นร้านอาหาร **Compute (EC2/Lambda)** คือพ่อครัวที่คอยปรุงอาหาร ส่วน **Database** คือตู้เก็บวัตถุดิบและสมุดจดสูตรอาหาร ถ้าตู้เก็บของหาของช้า หรือพังขึ้นมา ร้านอาหารก็ต้องหยุดทำงานทันที

ในบทนี้ เราจะมาทำความเข้าใจว่า AWS มีฐานข้อมูลแบบไหนบ้าง และเลือกใช้อย่างไรให้ระบบไม่ล่ม ทำงานเร็วระดับเสี้ยววินาที และประหยัดงบประมาณที่สุด

## ปูพื้นฐาน: เปรียบเทียบประเภทฐานข้อมูลแบบเข้าใจง่าย

หากไม่มีพื้นฐานด้าน Database มาก่อน ให้จินตนาการถึง 4 สิ่งนี้:

```
[ Relational / SQL ]          [ NoSQL ]                 [ Cache ]                  [ Data Warehouse ]
┌────────────────────┐     ┌─────────────────────┐    ┌─────────────────────┐    ┌─────────────────────┐
│ สมุดบัญชีตาราง     │     │ แฟ้มซองเอกสาร       │    │ กระดาษ Post-it       │    │ โกดังเก็บเอกสารเก่า │
│ มีตาราง มีแถว-คอลัมน์ │    │ แต่ละใบใส่ข้อมูลไม่เหมือนกัน│    │ แปะไว้บนโต๊ะ หยิบดูทันที│    │ รวมข้อมูล 10 ปีย้อนหลัง │
│ ตัวอย่าง: Amazon RDS│     │ ตัวอย่าง: DynamoDB  │    │ ตัวอย่าง: ElastiCache│    │ ตัวอย่าง: Redshift  │
└────────────────────┘     └─────────────────────┘    └─────────────────────┘    └─────────────────────┘
```

1. **Relational Database (SQL / RDBMS):**
   * *เปรียบเหมือน:* ตาราง Excel หรือสมุดบัญชี มีหัวข้อคอลัมน์ชัดเจน เช่น รหัสลูกค้า, ชื่อ, เบอร์โทร ข้อมูลมีความสัมพันธ์กัน (เช่น ตารางคำสั่งซื้อต้องผูกกับตารางลูกค้า)
   * *จุดเด่น:* ข้อมูลต้องถูกต้อง 100% ห้ามผิดพลาด (รองรับมาตรฐาน ACID) เช่น ยอดเงินในบัญชีธนาคาร
   * *ข้อจำกัด:* ขยายขนาด (Scale) เพื่อรองรับคนหลักล้านพร้อมกันได้ยากกว่า

2. **NoSQL (Non-relational Database):**
   * *เปรียบเหมือน:* แฟ้มใส่ซองเอกสาร แต่ละซอง (Item) จะมีรายละเอียดไม่เหมือนกันก็ได้ เช่น สินค้าชิ้นหนึ่งมีสีและไซส์ แต่อีกชิ้นมีแค่น้ำหนัก
   * *จุดเด่น:* รองรับทราฟฟิกระดับมหาศาล ขยายตัวอัตโนมัติ ตอบสนองเร็วคงที่ระดับเสี้ยววินาที (Single-digit millisecond)
   * *ข้อจำกัด:* ไม่เหมาะกับงานคำนวณที่ต้องเชื่อมโยงหลายตารางซับซ้อน (No Complex JOINs)

3. **In-Memory Cache:**
   * *เปรียบเหมือน:* กระดาษ Post-it หรือไวท์บอร์ดที่แปะไว้หน้าโต๊ะทำงาน สำหรับจดคำตอบที่ลูกค้าชอบถามซ้ำๆ
   * *จุดเด่น:* ข้อมูลถูกเก็บไว้ใน **หน่วยความจำหลัก (RAM)** แทนฮาร์ดดิสก์ จึงอ่านได้เร็วระดับ Microseconds (เร็วกว่า Database ทั่วไป 1,000 เท่า)

4. **Data Warehouse (OLAP):**
   * *เปรียบเหมือน:* โกดังเก็บเอกสารย้อนหลังหลายปี เอาไว้ให้ผู้บริหารเปิดดูรายงานแนวโน้มยอดขาย ไม่ได้ใช้รับออเดอร์หน้าร้านสดๆ

## 1. Amazon RDS (Relational Database Service)

AWS ช่วยดูแลเรื่องยากๆ ของฐานข้อมูล SQL ให้ เช่น การติดตั้ง, การอัปเดตความปลอดภัย (Patching), และการสำรองข้อมูล (Backup) อัตโนมัติ โดยรองรับ 6 เครื่องยนต์ฐานข้อมูลยอดนิยม:
* PostgreSQL, MySQL, MariaDB, Oracle, Microsoft SQL Server, และ Amazon Aurora

---

### 1.1 หัวใจสำคัญ: Multi-AZ vs Read Replicas (จุดดักข้อสอบอันดับ 1)

โจทย์ข้อสอบมักถามว่า *"ระบบช้าเพราะคนเปิดอ่านเยอะ"* หรือ *"ต้องการป้องกันกรณี Data Center ล่ม"* คุณต้องแยกสองสิ่งนี้ออกจากกันให้เด็ดขาด:

```
[ กรณีที่ 1: Multi-AZ เพื่อความอยู่รอด ]           [ กรณีที่ 2: Read Replicas เพื่อความเร็ว ]
       (เน้น Disaster Recovery)                         (เน้น Scaling การอ่าน)

     ┌───────────────┐                                ┌───────────────┐
     │ Primary DB    │ (เขียน/อ่าน)                     │ Primary DB    │ (เขียนข้อมูลเข้าที่นี่)
     │ (AZ-1a)       │                                │ (Master)      │
     └───────┬───────┘                                └───────┬───────┘
             │ Synchronous Copy                               │ Asynchronous Copy
             ▼ (เหมือนกันเป๊ะตลอดเวลา)                         ├──────────────────────┐
     ┌───────────────┐                                        ▼                      ▼
     │ Standby DB    │ (แสตนด์บายเฉยๆ                 ┌───────────────┐      ┌───────────────┐
     │ (AZ-1b)       │  ห้ามใครเข้าไปอ่าน)              │ Read Replica  │      │ Read Replica  │
     └───────────────┘                                │ (ช่วยแบ่งเบาอ่าน)│      │ (ข้าม Region ได้)│
                                                      └───────────────┘      └───────────────┘
```

| เกณฑ์เปรียบเทียบ | RDS Multi-AZ | RDS Read Replicas |
|---|---|---|
| **เป้าหมายหลัก** | **ความพร้อมใช้งานสูง (High Availability / DR)** | **เพิ่มประสิทธิภาพการเปิดอ่าน (Performance)** |
| **การทำงานเบื้องหลัง** | **Synchronous Replication** (ก๊อปปี้ข้อมูลแบบเรียลไทม์พร้อมกัน ข้อมูลไม่มีทางสูญหาย) | **Asynchronous Replication** (แอบก๊อปปี้ตามหลังมา อาจมีความล่าช้าหลักวินาที) |
| **บทบาทของตัวสำรอง** | เป็น **Standby ซ่อนอยู่เฉยๆ** ไม่สามารถเปิดให้ User หรือ App เข้าไปอ่านข้อมูลได้ | สามารถ **เชื่อมต่อเข้าไปอ่าน (Read-only)** เพื่อแบ่งเบาภาระของเครื่องหลักได้ |
| **เมื่อเครื่องหลักพัง** | **สลับอัตโนมัติ (Automated Failover)** โดยเปลี่ยน DNS CNAME ไปหา Standby ภายใน 1-2 นาที | **ไม่ Failover อัตโนมัติ** แต่ผู้ดูแลสามารถสั่งยกฐานะ (Promote) ขึ้นมาเป็น Master เครื่องใหม่ได้ |
| **การวางตำแหน่ง** | อยู่คนละ **AZ ภายใน Region เดียวกัน** | กระจายได้ทั้ง **ใน AZ เดียวกัน, ข้าม AZ, หรือข้ามไปต่าง Region ทั่วโลก** |

---

### 1.2 การสำรองข้อมูล (Automated Backups vs Manual Snapshots)
* **Automated Backups:**
  * AWS สำรองข้อมูลให้ทุกวัน พร้อมบันทึก Transaction Logs ตลอดเวลา
  * สามารถกู้คืนข้อมูลย้อนหลังกลับไปได้ถึงระดับ "เสี้ยววินาที" (Point-in-Time Recovery - PITR)
  * ตั้งระยะเวลาเก็บสำรองได้ตั้งแต่ **1 ถึง 35 วัน** (หากลบ RDS ทิ้ง Backup ชุดนี้จะถูกลบไปด้วย เว้นแต่จะระบุให้คงไว้)
* **Manual DB Snapshots:**
  * ผู้ดูแลเป็นคนกดสั่งสร้างเอง หรือตั้งสคริปต์สั่ง
  * **ไม่มีวันหมดอายุ** แม้จะสั่งลบเครื่อง RDS ทิ้ง Snapshot ตัวนี้ก็ยังคงอยู่ในระบบตลอดไป

## 2. Amazon Aurora (ฐานข้อมูลที่ AWS ออกแบบใหม่)

Amazon Aurora คือเครื่องยนต์ฐานข้อมูลแบบ Relational ของ AWS เอง (รองรับการใช้งานร่วมกับโปรแกรมเดิมที่เขียนด้วย MySQL และ PostgreSQL ได้ 100%)

### 2.1 สถาปัตยกรรม 6 สำเนา (6 Copies across 3 AZs)
สิ่งที่ทำให้ Aurora เหนือกว่า RDS ทั่วไป คือการแยก **ตัวประมวลผล (Compute)** ออกจาก **พื้นที่เก็บข้อมูล (Shared Storage)**:

```
                  ┌─── [AZ-1] ─── Copy 1  +  Copy 2
                  │
[ Aurora Storage ]┼─── [AZ-2] ─── Copy 3  +  Copy 4
(แชร์ร่วมกันทุกโหนด) │
                  └─── [AZ-3] ─── Copy 5  +  Copy 6
```

* ข้อมูลถูกก๊อปปี้เก็บไว้ **6 ชุด กระจายข้าม 3 Availability Zones** เสมอ
* สามารถทนต่อเหตุการณ์ **Data Center พัง 2 แห่งพร้อมกัน** ได้โดยที่ข้อมูลไม่สูญหาย
* การขยายขนาดพื้นที่ทำได้อัตโนมัติ (Auto-expanding) สูงสุดถึง **128 TB**

### 2.2 ฟีเจอร์เด่นของ Aurora ในข้อสอบ
* **Aurora Read Replicas:** สร้างได้สูงสุดถึง **15 เครื่อง** (ในขณะที่ RDS ทั่วไปทำได้แค่ 5 เครื่อง) และทุกเครื่องแชร์ Storage ก้อนเดียวกัน ทำให้ Replication Lag ต่ำระดับ Milliseconds
* **Aurora Serverless v2:** ปรับขนาด CPU และ RAM ขึ้น-ลงให้อัตโนมัติในระดับเสี้ยววินาที เหมาะกับระบบที่คาดเดาปริมาณคนใช้งานไม่ได้ เช่น แพลตฟอร์มขายบัตรคอนเสิร์ต
* **Aurora Global Database:** วางฐานข้อมูลกระจายตัวข้ามทวีป (Cross-Region) เพื่อให้คนทั่วโลกอ่านข้อมูลได้รวดเร็ว โดยมี Replication Lag ข้ามโลกน้อยกว่า 1 วินาที

## 3. Amazon DynamoDB (NoSQL ความเร็วระดับสายฟ้า)

Amazon DynamoDB เป็นฐานข้อมูลแบบ **Serverless NoSQL (Key-Value and Document)** จัดการโครงสร้างพื้นฐานให้อัตโนมัติ 100% ไม่ต้องเลือกขนาดเซิร์ฟเวอร์ ไม่ต้องอัปเดต OS

### 3.1 การค้นหาข้อมูล (Partition Key vs Sort Key)
* **Partition Key (PK / Hash Key):** คีย์หลักที่ระบบนำไปผ่านสูตรคณิตศาสตร์เพื่อเลือกเครื่องเซิร์ฟเวอร์ในการจัดเก็บ (ต้องกระจายตัวสม่ำเสมอ เช่น `User_ID`)
* **Sort Key (SK / Range Key):** คีย์รองที่ใช้จัดเรียงข้อมูลภายใน Partition เดียวกัน เช่น `Timestamp` หรือ `Transaction_ID`
* *ตัวอย่าง:* หาประวัติการซื้อของลูกค้า $PK = \text{User\_101}$, $SK = \text{2026-10-01}$

---

### 3.2 รูปแบบการคิดค่าบริการ (Capacity Modes)
1. **On-Demand Mode:**
   * คิดเงินตามจำนวนครั้งที่อ่านและเขียนจริง (Pay-per-request)
   * เหมาะสำหรับ: ระบบใหม่, ปริมาณโหลดคาดเดาไม่ได้, หรือทราฟฟิกพุ่งสูงฉับพลัน (Spiky workloads)
2. **Provisioned Mode (ตั้งค่าล่วงหน้า):**
   * กำหนดไว้ล่วงหน้าว่าต้องการขีดความสามารถในการอ่าน (RCU) และเขียน (WCU) เท่าไหร่ต่อวินาที
   * มีราคาถูกกว่ามากหากมีโหลดสม่ำเสมอ สามารถเปิด Auto-Scaling ร่วมด้วยได้

---

### 3.3 สี่ฟีเจอร์เด็ดของ DynamoDB ที่ต้องจำ
* **DynamoDB Streams:** บันทึกประวัติการเปลี่ยนแปลงข้อมูล (Insert, Update, Delete) แบบเรียลไทม์ เหมาะสำหรับการส่งต่อไป Trigger ให้ **AWS Lambda** ทำงานต่อ เช่น เมื่อมีคนสมัครสมาชิกใหม่ ให้ส่งอีเมลต้อนรับทันที
* **Time to Live (TTL):** กำหนดเวลาหมดอายุของข้อมูลอัตโนมัติ เมื่อถึงเวลาที่ระบุ ระบบจะลบข้อมูลทิ้งให้ฟรี โดยไม่เสียค่า WCU (เหมาะสำหรับเก็บ Session ผู้ใช้ หรือบันทึกประวัติชั่วคราว)
* **Global Tables:** ทำระบบฐานข้อมูลแบบ **Multi-Region Active-Active** เขียนหรืออ่านที่สิงคโปร์ ข้อมูลจะซิงค์ไปโผล่ที่อเมริกาในเสี้ยววินาที
* **DynamoDB Accelerator (DAX):** ชิปแคชความเร็วสูงสำหรับ DynamoDB โดยเฉพาะ ช่วยเร่งความเร็วในการอ่านข้อมูลขึ้น 10 เท่า จากระดับ Milliseconds กลายเป็น **Microseconds**

## 4. In-Memory Caching: ElastiCache vs DAX

แคช (Cache) คือการเอาข้อมูลที่ถูกเรียกดูซ้ำๆ ขึ้นมาวางไว้บนหน่วยความจำ RAM เพื่อลดภาระของฐานข้อมูลหลัก

```
[ ผู้ใช้งาน / App ] ──── 1. ขอดูข้อมูลสินค้าหน่อย ───> [ Caching Layer ]
       ▲                                                    │
       │                                            (พบข้อมูล: Cache Hit!)
       └────────────── 2. ตอบกลับทันที (Microseconds) ──────┘
                                                            │
                                                    (ไม่พบ: Cache Miss)
                                                            ▼
                                                   [ ฐานข้อมูลหลัก (RDS/DB) ]
```

### 4.1 ElastiCache: Redis vs Memcached

| คุณสมบัติ | Redis OSS / Valkey | Memcached |
|---|---|---|
| **โครงสร้างข้อมูล** | ซับซ้อน (Strings, Hashes, Lists, Sets, Geospatial) | เก็บแบบ Key-Value อย่างง่าย |
| **ความทนทาน (Persistence)** | **มี (บันทึกข้อมูลลงดิสก์ได้ กู้คืนได้)** | **ไม่มี (ไฟดับหรือปิดเครื่อง ข้อมูลหาย 100%)** |
| **High Availability** | รองรับ **Multi-AZ พร้อม Automatic Failover** และ Read Replicas | ทำงานแยกโหนดเดี่ยวๆ ไม่มี Failover ในตัว |
| **Use Cases** | แคชทั่วไป, จัดอันดับคะแนนเกม (Leaderboards), จัดการ Session, Pub/Sub | ทำแคชหน้าเว็บธรรมดาที่ข้อมูลหายแล้วไปดึงใหม่ได้ ไม่ซับซ้อน |

---

### 4.2 เมื่อไหร่ใช้ DAX? เมื่อไหร่ใช้ ElastiCache?
* **เลือก DAX:** เมื่อฐานข้อมูลหลักของคุณคือ **DynamoDB เท่านั้น** และต้องการความเร็วระดับ Microseconds โดยไม่ต้องเขียนโค้ดแก้ตรรกะของแอปใหม่
* **เลือก ElastiCache:** เมื่อต้องการแคชผลลัพธ์ของคำสั่ง SQL จาก **Amazon RDS**, ทำระบบ Session Store ข้ามเซิร์ฟเวอร์, หรือเก็บข้อมูลโครงสร้างเฉพาะ

## 5. Specialty Databases (รู้จักไว้ตัดช้อยส์)

| บริการ | ประเภท | เหมาะกับงานแบบไหน? | คีย์เวิร์ดในข้อสอบ |
|---|---|---|---|
| **Amazon Redshift** | Data Warehouse (OLAP) | วิเคราะห์ข้อมูลขนาดใหญ่ระดับ Petabytes, ทำรายงาน Business Intelligence (BI) | **SQL analytics, Columnar storage, BI reporting, OLAP** |
| **Amazon DocumentDB** | Document NoSQL | รองรับคำสั่งของ **MongoDB** โดยไม่ต้องดูแลเครื่องเอง | **MongoDB compatible, JSON documents** |
| **Amazon Neptune** | Graph Database | จัดการข้อมูลที่มีความสัมพันธ์โยงใยซับซ้อน เช่น แพลตฟอร์ม Social Media, เครือข่ายตรวจจับการฉ้อโกงบัตรเครดิต | **Social network graph, Fraud detection, Knowledge graph** |
| **Amazon OpenSearch** | Search Engine & Log Analytics | ระบบค้นหาข้อความในเว็บ (Full-text search) และวิเคราะห์ Log ระบบ | **Full-text search, Log analytics, Kibana dashboards** |

## 6. Exam Trap & Keyword Decision Matrix

ตารางสรุปคีย์เวิร์ดตัดสินใจสำหรับหมวดฐานข้อมูล:

| โจทย์ระบุคีย์เวิร์ด (Exam Trigger) | ตัดสินใจเลือกใช้ (Architecture Decision) | เหตุผลและจุดหลอก |
|---|---|---|
| *"High availability for database, automatic failover with zero data loss"* | **RDS Multi-AZ** | Multi-AZ สร้างขึ้นมาเพื่อกันระบบล่ม ไม่ได้ช่วยเรื่องความเร็วในการเปิดอ่าน |
| *"Database performance bottleneck due to heavy read traffic across the globe"* | **RDS Read Replicas (Cross-Region)** | เพิ่ม Read Replicas ช่วยแบ่งเบาโหลดอ่าน และวางข้ามทวีปให้คนเปิดอ่านเร็วขึ้น |
| *"Sub-millisecond latency for DynamoDB read-heavy application"* | **DynamoDB Accelerator (DAX)** | คำว่า "Sub-millisecond" ผูกกับ "DynamoDB" ให้มองหา DAX เป็นตัวเลือกแรก |
| *"Complex SQL queries, multi-table JOINs, transactional financial system"* | **Amazon RDS หรือ Amazon Aurora** | งานที่มีความสัมพันธ์ซับซ้อนและเน้นความถูกต้องทางบัญชี ห้ามตอบ NoSQL / DynamoDB เด็ดขาด |
| *"Store user sessions with automatic expiration, zero maintenance cost"* | **DynamoDB พร้อมเปิด Time to Live (TTL)** | การลบข้อมูล Session ที่หมดอายุอัตโนมัติเป็นหน้าที่หลักของ DynamoDB TTL |
| *"Large-scale data warehousing, run complex analytical queries on years of data"* | **Amazon Redshift** | งานวิเคราะห์ข้อมูลเก่าหรือทำรายงาน BI ชี้เป้าไปที่ Redshift เสมอ (ไม่ใช่ RDS) |
| *"Multi-region active-active database with seamless replication"* | **DynamoDB Global Tables** | หากโจทย์ระบุ Active-Active ข้ามทวีปและเป็น NoSQL คำตอบคือ Global Tables |
