# Module 3: Storage & Data Lifecycle

ในโลกของ Cloud คำว่า "ที่เก็บข้อมูล" ไม่ได้มีแค่ฮาร์ดดิสก์แบบเดียวเหมือนในคอมพิวเตอร์ทั่วไป AWS แบ่งประเภท Storage ออกตามพฤติกรรมการใช้งานจริง เพื่อให้ระบบทำงานได้เร็วที่สุดและจ่ายเงินน้อยที่สุด

---

## ปูพื้นฐาน: เปรียบเทียบ Storage 3 รูปแบบหลักในโลกไอที

หากไม่มีพื้นฐานมาก่อน ให้จินตนาการ Storage 3 ประเภทนี้ด้วยสิ่งของในชีวิตประจำวัน:

```
[ Block Storage (EBS) ]        [ File Storage (EFS / FSx) ]       [ Object Storage (S3) ]
┌───────────────────────┐      ┌──────────────────────────┐      ┌─────────────────────────┐
│ ฮาร์ดดิสก์ / SSD      │      │ โฟลเดอร์แชร์ในออฟฟิศ      │      │ จุดรับฝากสัมภาระ        │
│ เสียบตรงเข้าคอม 1 เครื่อง│     │ ทุกเครื่องในแผนกเปิดดูพร้อมกัน│      │ ฝากไฟล์แล้วได้ใบเสร็จ URL │
│ แก้งานระดับ 1 ตัวอักษรได้ │    │ มีโครงสร้าง Folder ลำดับชั้น  │      │ แก้ไฟล์ต้องอัปโหลดทับใหม่│
└───────────────────────┘      └──────────────────────────┘      └─────────────────────────┘
```

1. **Block Storage (เช่น Amazon EBS):**
   * *เปรียบเหมือน:* ฮาร์ดดิสก์แบบ SSD หรือ Flash drive ที่เราเอาสายเสียบเข้าช่องคอมพิวเตอร์ตรงๆ
   * *การทำงาน:* ข้อมูลถูกหั่นเป็นชิ้นเล็กๆ เรียกว่า "Block" เหมาะสำหรับการรันระบบปฏิบัติการ (OS) หรือติดตั้งฐานข้อมูล เพราะอ่านเขียนได้เร็วระดับเสี้ยววินาที และแก้คำผิดแค่คำเดียวในไฟล์ได้โดยไม่ต้องเซฟใหม่ทั้งไฟล์
   * *ข้อจำกัด:* ปกติจะเสียบใช้งานได้กับคอมพิวเตอร์ (EC2) ทีละเครื่องเท่านั้น

2. **File Storage (เช่น Amazon EFS, FSx):**
   * *เปรียบเหมือน:* โฟลเดอร์แชร์ส่วนกลางในออฟฟิศ หรือ Google Drive ในคอม
   * *การทำงาน:* มีโฟลเดอร์ย่อย มีลำดับชั้น (Hierarchical Directory) ชัดเจน เช่น `/documents/project/file.pdf`
   * *จุดเด่น:* เครื่องคอมพิวเตอร์หลายสิบหรือหลายร้อยเครื่อง สามารถเชื่อมต่อเข้ามาเปิดอ่านและแก้ไขไฟล์พร้อมกันได้ทันที

3. **Object Storage (เช่น Amazon S3):**
   * *เปรียบเหมือน:* จุดรับฝากของ หรือตู้ล็อคเกอร์อัจฉริยะ
   * *การทำงาน:* ข้อมูลจะถูกเก็บเป็น "ก้อนเดี่ยวๆ (Object)" ประกอบด้วย **ข้อมูลตัวไฟล์ + ข้อมูลอธิบาย (Metadata) + รหัสบัตรคิว (Unique Key / URL)**
   * *จุดเด่น:* เก็บไฟล์ได้ไม่จำกัด จะฝากรูป 1 รูป หรือ 100 ล้านรูปก็ไม่ต้องกังวลเรื่องพื้นที่เต็ม เข้าถึงไฟล์ผ่านลิงก์อินเทอร์เน็ต (HTTP/HTTPS) ได้โดยตรง
   * *ข้อจำกัด:* ไม่สามารถเปิดเข้าไปแก้ข้อความแค่ 1 บรรทัดได้ หากต้องการแก้ ต้องอัปโหลดไฟล์เวอร์ชันใหม่ขึ้นไปทับทั้งไฟล์

## 1. Amazon S3 (Simple Storage Service)

Amazon S3 คือบริการ Object Storage ที่ได้รับความนิยมสูงสุดบน AWS ออกแบบมาให้ข้อมูลไม่มีวันสูญหาย

### 1.1 ความทนทานและความพร้อมใช้งาน (Durability vs Availability)
* **Durability (ความทนทาน):** การันตีที่ **$99.999999999\%$ (11 9's)**
  * *แปลความหมายง่ายๆ:* หากคุณเก็บไฟล์ไว้ 10,000,000 ไฟล์บน S3 คุณอาจจะต้องใช้เวลาเฉลี่ยถึง 10,000 ปี ถึงจะมีโอกาสสูญหายเพียงแค่ 1 ไฟล์ เพราะ AWS จะก๊อปปี้ข้อมูลของคุณกระจายไปเก็บไว้ใน Data Center อย่างน้อย 3 แห่ง (3 AZs) อัตโนมัติ
* **Availability (ความพร้อมใช้งาน):** หมายถึงโอกาสที่ระบบเปิดให้คุณคลิกเข้าไปดาวน์โหลดหรือเปิดดูไฟล์ได้สำเร็จ (ปกติอยู่ที่ $99.9\% - 99.99\%$)

---

### 1.2 ตารางเปรียบเทียบ S3 Storage Classes (ระดับชั้นการเก็บไฟล์)

ข้อสอบ SAA จะออกเรื่องการเลือก Storage Class เพื่อประหยัดเงินมากที่สุด:

| Storage Class | พฤติกรรมการเปิดใช้งาน | ค่าเก็บไฟล์ ($/GB) | ค่าดึงข้อมูล ($/GB) | ระยะเวลาฝากขั้นต่ำ | ระยะเวลาในการรอโหลดไฟล์ |
|---|---|---|---|---|---|
| **S3 Standard** | เปิดบ่อยมาก, ต้องการความเร็วสูง | สูงสุด | ฟรี | ไม่มี | ทันที (Milliseconds) |
| **S3 Intelligent-Tiering** | ไม่แน่ใจ pattern การเข้าถึง | เท่า Standard | ฟรี | 30 วัน | ทันที (ใช้ Machine Learning สลับ Tier ให้เองอัตโนมัติ) |
| **S3 Standard-IA (Infrequent Access)** | เดือนละครั้ง หรือนานๆ เปิดที | ถูกลง ~50% | มีค่าธรรมเนียม | 30 วัน | ทันที (Milliseconds) |
| **S3 One Zone-IA** | ไฟล์ไม่สำคัญ, สร้างใหม่เองได้ | ถูกลง ~60% | มีค่าธรรมเนียม | 30 วัน | ทันที (เก็บแค่ 1 AZ หากตึกล่ม ข้อมูลหาย) |
| **S3 Glacier Instant Retrieval** | ข้อมูลเก่า ไตรมาสละครั้ง แต่ตอนจะดูต้องได้ทันที | ถูกมาก | มีค่าธรรมเนียม | 90 วัน | ทันที (Milliseconds) |
| **S3 Glacier Flexible Retrieval** | ข้อมูลสำรอง (Backup) รอได้ระดับชั่วโมง | ถูกมากเป็นพิเศษ | ถูก | 90 วัน | **Expedited:** 1-5 นาที<br>**Standard:** 3-5 ชั่วโมง<br>**Bulk:** 5-12 ชั่วโมง |
| **S3 Glacier Deep Archive** | เก็บตามกฎหมาย 7-10 ปี แทบไม่เคยเปิดดู | ถูกที่สุดใน AWS | ถูก | 180 วัน | **Standard:** 12 ชั่วโมง<br>**Bulk:** 48 ชั่วโมง |

---

### 1.3 วงจรชีวิตของข้อมูล (S3 Lifecycle Rules)
แทนที่จะให้คนมาคอยกดลบไฟล์ คุณสามารถตั้งกฎอัตโนมัติได้ เช่น:
```
[ วันที่ 0: ลูกค้าอัปโหลดรูปใบเสร็จ ] ──> S3 Standard
                                      │
  (ผ่านไป 30 วัน: ลูกค้าไม่ค่อยเปิดดูแล้ว)
                                      ▼
[ วันที่ 30: ย้ายอัตโนมัติ ] ─────────> S3 Standard-IA (ประหยัดค่าใช้จ่ายลงครึ่งหนึ่ง)
                                      │
  (ผ่านไป 90 วัน: ปิดงบบัญชีประจำไตรมาส)
                                      ▼
[ วันที่ 90: ย้ายเข้าคลังเก็บถาวร ] ───> S3 Glacier Flexible (ประหยัดค่าใช้จ่ายสูงสุด)
                                      │
  (ผ่านไป 365 วัน: หมดอายุความทางภาษี)
                                      ▼
[ วันที่ 365: ลบทิ้งถาวร ] ──────────> Permanently Deleted (Expire)
```

---

### 1.4 ความปลอดภัยและการป้องกันการลบข้อมูลบน S3
* **Versioning (ระบบจำประวัติไฟล์):** ป้องกันการกดลบหรือเซฟทับโดยไม่ได้ตั้งใจ หากเปิดไว้ เมื่อมีคนกดลบ S3 จะแค่แปะป้าย `Delete Marker` บังตาไว้ แต่ไฟล์เก่ายังอยู่และกู้คืนได้เสมอ
* **MFA Delete:** บังคับให้ต้องกรอกรหัส OTP จากอุปกรณ์ Authenticator ก่อนจะสั่งลบไฟล์หรือปิด Versioning ได้
* **S3 Object Lock (WORM - Write Once, Read Many):** ป้องกันไม่ให้ใครก็ตามแก้ไขหรือลบไฟล์ได้เด็ดขาด มี 2 โหมด:
  1. **Compliance Mode:** เข้มงวดสูงสุด **แม้แต่เจ้าของบัญชี หรือ Root User ของ AWS ก็สั่งลบไม่ได้** จนกว่าจะครบกำหนดเวลา (ใช้สำหรับงานกฎหมาย การเงิน และหลักทรัพย์)
  2. **Governance Mode:** คนทั่วไปลบไม่ได้ แต่สามารถให้สิทธิ์พิเศษ (Specific IAM Permission) แก่ Admin บางคนเพื่อปลดล็อกหรือลบก่อนเวลาได้

## 2. Amazon EBS (Elastic Block Store)

เปรียบเสมือนฮาร์ดดิสก์ที่คุณนำไปเสียบเข้ากับเครื่อง EC2 เพื่อรัน Windows หรือ Linux

### 2.1 คำศัพท์สำคัญ: IOPS vs Throughput
* **IOPS (Input/Output Operations Per Second):** *จำนวนครั้ง* ในการอ่านเขียนต่อหนึ่งวินาที 
  * เปรียบเหมือน **"จำนวนรอบของรถมอเตอร์ไซค์ส่งอาหาร"** เหมาะกับงานอ่านเขียนข้อมูลชิ้นเล็กๆ ถี่ๆ เช่น ระบบ Database (SQL / NoSQL)
* **Throughput:** *ปริมาณเนื้อข้อมูล* ที่วิ่งผ่านต่อหนึ่งวินาที (วัดเป็น MB/s)
  * เปรียบเหมือน **"รถบรรทุกคันใหญ่ที่ขนทรายทีละมากๆ"** เหมาะกับงานดูหนัง Streaming, วิเคราะห์ข้อมูล Big Data, หรือประมวลผลไฟล์ Log ขนาดยักษ์

---

### 2.2 ตารางสรุปประเภทของ EBS Volumes

| Volume Type | ชนิดฮาร์ดดิสก์ | เหมาะสำหรับงานแบบไหน? | คีย์เวิร์ดในข้อสอบ SAA |
|---|---|---|---|
| **General Purpose SSD (gp3)** | SSD ยุคใหม่ | ใช้งานทั่วไป, ระบบ Web App, Dev/Test | คุ้มค่าที่สุด, ปรับแต่ง IOPS และ Throughput แยกจากขนาดดิสก์ได้อิสระ |
| **General Purpose SSD (gp2)** | SSD รุ่นเก่า | ระบบทั่วไปยุคก่อน | IOPS จะผูกติดกับขนาดความจุของดิสก์ (ยิ่งซื้อดิสก์ใหญ่ ยิ่งได้ IOPS เยอะ) |
| **Provisioned IOPS SSD (io2 / io1)** | High-End SSD | ฐานข้อมูลขนาดใหญ่ที่ต้องการความเร็วสูงมาก และห้ามสะดุด | **Sub-millisecond latency, Critical DB**, ต้องการ IOPS มากกว่า 16,000 ขึ้นไป |
| **Throughput Optimized HDD (st1)** | จานหมุน (HDD) | งาน Big Data, Data Warehouse, Kafka | **Throughput intensive, sequential I/O**, ห้ามใช้เป็น Boot Volume (ไดรฟ์ C) |
| **Cold HDD (sc1)** | จานหมุน (HDD) | งานเก็บข้อมูลที่ไม่ได้เปิดบ่อย แต่ต้องการ Block Storage ราคาถูก | ต้นทุนต่ำสุดสำหรับ HDD, ข้อมูลเข้าถึงน้อย |

> **กฎเหล็กของ EBS ในข้อสอบ:**
> 1. EBS Volume จะผูกติดอยู่กับ **Availability Zone (AZ) เดียวกันกับ EC2 เสมอ** (ไม่สามารถเอา EBS ใน AZ-1a ไปเสียบตรงๆ ให้ EC2 ใน AZ-1b ได้)
> 2. หากต้องการย้าย EBS ข้าม AZ หรือข้าม Region ต้องทำผ่านการถ่ายภาพ **Snapshot** ก่อนเสมอ (Snapshot จะถูกส่งไปเก็บไว้บน Amazon S3 โดยอัตโนมัติ)
> 3. **EBS Multi-Attach:** อนุญาตให้ EBS ก้อนเดียว เสียบเข้ากับ EC2 ได้หลายเครื่องพร้อมกัน **ใช้ได้เฉพาะประเภท io1/io2 และต้องอยู่ภายใน AZ เดียวกันเท่านั้น**

## 3. Shared File Systems: EFS vs FSx

เมื่อต้องการให้คอมพิวเตอร์หลายร้อยเครื่องเปิดไฟล์ในโฟลเดอร์เดียวกันพร้อมๆ กัน (Shared File Storage)

```
                       ┌─── Amazon EFS ───────────────> สำหรับระบบ Linux (POSIX) ขยายขนาดได้ไม่จำกัด
                       │
[ ระบบแชร์ไฟล์ส่วนกลาง ] ──┼─── FSx for Windows ──────────> สำหรับ Windows (SMB, Active Directory)
                       │
                       └─── FSx for Lustre ───────────> สำหรับงานคำนวณเร็วระดับมหาศาล (HPC / AI / ML)
```

### ตารางเปรียบเทียบเพื่อการตัดสินใจ

| คุณสมบัติ | Amazon EFS | FSx for Windows | FSx for Lustre |
|---|---|---|---|
| **ระบบปฏิบัติการที่รองรับ** | **Linux เท่านั้น** | **Windows & Linux** | **Linux (เน้นงาน HPC)** |
| **โปรโตคอลเครือข่าย** | NFSv4 (POSIX compliant) | SMB protocol, NTFS | Lustre High-performance FS |
| **การกระจายตัว** | กระจายข้าม **Multi-AZ อัตโนมัติ** | เลือกได้ทั้ง Single-AZ หรือ Multi-AZ | ออกแบบมาสำหรับงานประมวลผลด่วนชั่วคราว |
| **การรองรับผู้ใช้ของระบบ** | Linux user permissions | รองรับ **Microsoft Active Directory** | POSIX permissions |
| **จุดเชื่อมโยงพิเศษ** | ย้ายไฟล์เก่าลง EFS Archive ได้ | มีระบบ Deduplication ลดขนาดไฟล์ | **เชื่อมต่อดึงข้อมูลเข้า-ออกจาก S3 ได้โดยตรง** |

## 4. Hybrid Storage & Data Transfer (การขนย้ายข้อมูลระหว่างออฟฟิศกับ AWS)

สำหรับบริษัทที่มีศูนย์ข้อมูล (On-Premises) ของตนเอง และต้องการเชื่อมต่อพื้นที่เก็บข้อมูลกับ AWS:

### 4.1 AWS Storage Gateway (สะพานเชื่อมพื้นที่จัดเก็บ)
* **S3 File Gateway:** ทำให้ออฟฟิศมองเห็น Amazon S3 เป็นเหมือนไดรฟ์แชร์ในวงแลน (ผ่านโปรโตคอล NFS หรือ SMB) ไฟล์ใหม่จะถูกซิงค์ขึ้น S3 อัตโนมัติ
* **Volume Gateway:** ทำให้เซิร์ฟเวอร์ในออฟฟิศมองเห็น AWS เป็นฮาร์ดดิสก์ก้อนหนึ่ง (iSCSI):
  * *Cached Volume:* เก็บข้อมูลที่เปิดบ่อยไว้ที่ออฟฟิศ ส่วนข้อมูลหลักทั้งหมดเก็บไว้บน AWS Cloud (เหมาะกับที่ที่ออฟฟิศมีฮาร์ดดิสก์จำกัด)
  * *Stored Volume:* เก็บข้อมูลทั้งหมด 100% ไว้ที่ออฟฟิศก่อน แล้วคอยแอบสำรองข้อมูล (Backup Snapshot) ขึ้น Cloud เบื้องหลัง
* **Tape Gateway:** ใช้ทดแทนตู้เทปสำรองข้อมูลแบบโบราณ โดยข้อมูลจะถูกส่งไปเก็บไว้บน S3 Glacier แทน

### 4.2 ขนย้ายข้อมูลขนาดใหญ่ด้วย AWS Snow Family
เมื่อข้อมูลมีขนาดมหาศาล (หลายสิบ Terabytes จนถึงหลัก Petabytes) การส่งผ่านสายอินเทอร์เน็ตอาจต้องใช้เวลานานหลายเดือน AWS จะส่งอุปกรณ์ฮาร์ดแวร์จริงใส่กล่องกันกระแทกมาให้ถึงออฟฟิศ:

```
[ ข้อมูล 10TB - 50TB ] ────────> AWS Snowcone (ขนาดกะทัดรัด น้ำหนักเบา ขนย้ายง่าย)
[ ข้อมูล 50TB - หลายร้อย TB ] ──> AWS Snowball Edge (กล่องนิรภัย มีหน่วยประมวลผลในตัว)
[ ข้อมูลระดับ Exabytes ] ──────> AWS Snowmobile (รถบรรทุกคอนเทนเนอร์ขนาดใหญ่ วิ่งไปจอดหน้า Data Center)
```

## 5. Exam Trap & Keyword Decision Matrix

ตารางสรุปคีย์เวิร์ดดักทางข้อสอบสำหรับหมวด Storage:

| โจทย์ระบุคีย์เวิร์ด (Exam Trigger) | ตัดสินใจเลือกใช้ (Architecture Decision) | เหตุผลและจุดหลอก |
|---|---|---|
| *"POSIX-compliant, shared storage across thousands of EC2 Linux instances"* | **Amazon EFS** | คีย์เวิร์ด "POSIX" และ "Linux Shared" ชี้เป้าไปที่ EFS เสมอ |
| *"Shared file system for Windows instances integrated with Microsoft AD"* | **Amazon FSx for Windows File Server** | โจทย์ระบุ Windows และ Active Directory ตอบ FSx for Windows ทันที |
| *"High Performance Computing (HPC), machine learning, sub-millisecond, integration with S3"* | **Amazon FSx for Lustre** | งานคำนวณความเร็วสูงที่มีการดึงข้อมูลจาก S3 เข้ามาประมวลผล ต้องเป็น Lustre |
| *"Strict regulatory compliance, data cannot be deleted even by root account"* | **S3 Object Lock in Compliance Mode** | Governance mode อนุญาตให้ IAM พิเศษลบได้ แต่ Compliance mode ป้องกันทุกคนเด็ดขาด |
| *"Move data to lower cost tier if not accessed for 30 days, unpredictable pattern"* | **S3 Intelligent-Tiering** | ถ้าโจทย์บอกว่า "Unpredictable access pattern" (เดาความถี่ไม่ได้) ตอบ Intelligent-Tiering เสมอ |
| *"Attach a single block storage volume to multiple EC2 instances concurrently"* | **EBS Multi-Attach (io1 or io2 only)** | gp2/gp3 ทำ Multi-attach ไม่ได้ ต้องใช้ตระกูล Provisioned IOPS (io1/io2) เท่านั้น |
| *"Replace on-premises physical tape backups without changing existing backup software"* | **AWS Storage Gateway - Tape Gateway** | คีย์เวิร์ดคือ "Physical Tape Backup" แทนที่ด้วย Tape Gateway |
