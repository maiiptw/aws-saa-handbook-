# Module 5: Decoupled & Event-Driven Systems

ในระบบไอทีแบบดั้งเดิม ส่วนประกอบต่างๆ มักจะ "ผูกติดกันแน่น (Tightly Coupled)" เช่น เมื่อลูกค้ากดสั่งซื้อของ หน้าเว็บต้องรอให้ระบบตัดเงินทำงานเสร็จ $\rightarrow$ รอระบบตัดสต็อกทำงานเสร็จ $\rightarrow$ รอระบบส่งอีเมลยืนยันทำงานเสร็จ ลูกค้าถึงจะเห็นหน้าจอว่า "สั่งซื้อสำเร็จ"

**ปัญหาคือ:** ถ้าวันไหนระบบส่งอีเมลค้างหรือพัง ระบบสั่งซื้อของทั้งระบบจะพังตามไปด้วยทันที!

AWS จึงสอนให้เราออกแบบระบบแบบ **"แยกส่วน (Decoupled / Loosely Coupled)"** โดยใช้ **คิวข้อความ (Message Queues)** และ **ระบบกระจายข่าว (Event-Driven)** มาคั่นกลาง

---

## ปูพื้นฐาน: เปรียบเทียบ Decoupling กับ "ร้านกาแฟชานมไข่มุก"

```
[ ระบบแบบเดิม (Tightly Coupled) ]
ลูกค้าสั่งกาแฟ ──> พนักงานรับออเดอร์ต้องยืนรอจนกว่าบาริสต้าจะชงเสร็จ ──> ค่อยหันไปรับลูกค้าคนถัดไป
                  (ถ้าบาริสต้าชงช้า หน้าร้านแถวยาวเหยียด / ถ้าบาริสต้าเป็นลม ร้านเจ๊งทันที)

[ ระบบแยกส่วน (Decoupled ด้วย SQS) ]
ลูกค้าสั่งกาแฟ ──> พนักงานรับเงิน ──> ปริ้นท์ "บัตรคิว" เสียบไว้ที่ราง ──> หันไปรับลูกค้าคนถัดไปทันที
                                             │
                                        [ รางใส่บัตรคิว (Queue) ]
                                             │
                                       บาริสต้าค่อยๆ ทยอยดึงคิวไปชง
                 (ลูกค้าหน้าร้านมาพร้อมกัน 1,000 คนก็รับไหว บาริสต้าก็ชงตามกำลัง ไม่ล่ม)
```

## 1. Amazon SQS (Simple Queue Service)

Amazon SQS คือบริการ **รางใส่บัตรคิว (Message Queue)** แบบ Serverless ขยายตัวได้ไม่จำกัด เพื่อรับฝากข้อความไว้ชั่วคราวระหว่างระบบ 2 ตัว

```
[ Producer: ผู้ส่งข้อความ ] ──ส่งข้อความ──> [ SQS Queue ] ──ดึงข้อความไปประมวลผล──> [ Consumer: ผู้รับงาน ]
(เช่น เว็บรับออเดอร์)                         (รางเก็บข้อความ)                           (เช่น EC2 / Lambda ตัดสต็อก)
```

### 1.1 ประเภทของคิว: Standard Queue vs FIFO Queue (จุดออกสอบประจำ)

| คุณสมบัติ | Standard Queue (คิวมาตรฐาน) | FIFO Queue (คิวเรียงลำดับเป๊ะ) |
|---|---|---|
| **การเรียงลำดับ** | **Best-effort ordering** (พยายามเรียงให้ แต่อาจมีบางข้อความแซงคิวกันได้) | **First-In, First-Out 100%** (เข้าก่อน ออกก่อน ลำดับถูกต้องสมบูรณ์แบบ) |
| **การส่งซ้ำ** | **At-least-once delivery** (ส่งอย่างน้อย 1 ครั้ง แต่อาจมีข้อความเดิมหลุดซ้ำมาได้) | **Exactly-once processing** (รับประกันไม่มีข้อความซ้ำแน่นอน ด้วย Deduplication ID) |
| **ความเร็ว Throughput** | **ไม่จำกัด (Unlimited)** รับได้หลักหมื่น/หลักแสนข้อความต่อวินาที | สูงสุด 300 ข้อความ/วินาที (หรือ 3,000 ข้อความ/วินาที หากเปิด Batching) |
| **การตั้งชื่อ** | ตั้งชื่ออะไรก็ได้ เช่น `order-queue` | **ต้องลงท้ายด้วย `.fifo` เสมอ** เช่น `banking-order.fifo` |
| **Use Cases** | งานทั่วไปที่เร็วและทนต่อการทำซ้ำได้ เช่น งาน Resize รูปภาพ, ส่ง SMS | งานการเงิน, ยอดเงินในบัญชี, จองตั๋วคอนเสิร์ต (ลำดับใครมาก่อน-หลังสำคัญที่สุด) |

---

### 1.2 สี่กลไกการทำงานของ SQS ที่ต้องจำให้ขึ้นใจ

1. **Visibility Timeout (ช่วงเวลาบังตาคนอื่น):**
   * เมื่อ Consumer ตัวหนึ่งดึงข้อความจากคิวไปเริ่มทำ ข้อความนั้นจะ **"หายตัวไปชั่วคราว"** จากคิว เพื่อไม่ให้ Consumer ตัวอื่นมาแย่งดึงงานเดียวกันไปทำซ้ำ
   * *ค่า Default:* 30 วินาที
   * *จุดดักข้อสอบ:* หาก Consumer ประมวลผลงานยังไม่เสร็จแล้วครบ 30 วินาที ข้อความจะโผล่กลับมาในคิว ทำให้ Consumer ตัวอื่นหยิบไปทำซ้ำ $\rightarrow$ วิธีแก้คือ Application ต้องส่งคำสั่ง `ChangeMessageVisibility` เพื่อขอขยายเวลาเพิ่ม
2. **Dead-Letter Queue (DLQ - ถังขยะงานเสีย):**
   * หากข้อความหนึ่งมีปัญหา (เช่น มีบั๊กในโค้ด) ทำให้ทำไม่เสร็จสักที และวนกลับมาทำซ้ำจนเกินจำนวนรอบที่กำหนด (`maxReceiveCount`)
   * SQS จะย้ายข้อความนั้นไปเก็บไว้ใน **DLQ** แยกต่างหาก เพื่อไม่ให้มาขวางคิวของงานอื่น และให้นักพัฒนาเข้ามาตรวจสอบข้อผิดพลาดภายหลัง
3. **Long Polling (`ReceiveMessageWaitTimeSeconds`):**
   * *Short Polling (แบบเดิม):* Consumer วิ่งไปถามคิวทันที ถ้าไม่มีของก็กลับมือเปล่า ทำให้เปลืองจำนวน Request และเสียเงินฟรี
   * *Long Polling:* Consumer วิ่งไปถามแล้ว **"ยืนรออยู่ตรงนั้นสูงสุด 20 วินาที"** หากมีข้อความเข้ามาปุ๊บ จะส่งให้ทันที $\rightarrow$ **ช่วยลด Cost และลดความหน่วง (Latency)**
4. **Auto Scaling ร่วมกับ SQS:**
   * การสเกล EC2 ตามจำนวนงานในคิว **ห้ามใช้ CPU Utilization ของ EC2 เด็ดขาด** (เพราะ CPU อาจต่ำแต่งานค้างมหาศาล)
   * ต้องใช้ Metric ของ CloudWatch ชื่อ: **`ApproximateNumberOfMessagesVisible`** (จำนวนข้อความที่รออยู่ในคิว)

## 2. Amazon SNS (Simple Notification Service)

หาก SQS คือ "รางบัตรคิว" **Amazon SNS จะเปรียบเหมือน "ลำโพงเสียงตามสาย หรือ แชตกลุ่ม"** ทำงานแบบ **Pub/Sub (Publish / Subscribe)** โดยมีผู้ส่งข่าว 1 คน และมีผู้รับข่าวสารหลายคนพร้อมกัน (Fanout)

```
                                                     ┌──> [ SQS: แผนกตัดสต็อกสินค้า ]
                                                     │
[ เว็บสั่งซื้อ ] ──ประกาศข่าว "มีออเดอร์ใหม่"──> [ SNS Topic ] ──┼──> [ SQS: แผนกออกใบเสร็จภาษี ]
                                                     │
                                                     └──> [ Lambda: ส่งแจ้งเตือน Line/SMS ]
```

### 2.1 SNS + SQS Fanout Pattern (สถาปัตยกรรมสุดฮิตในข้อสอบ)
* **ปัญหา:** เว็บขายของต้องการให้เมื่อมีออเดอร์เข้ามา 1 ครั้ง ต้องทำ 3 อย่างพร้อมกัน: ตัดสต็อก, ออกใบเสร็จ, และแจ้งเตือนขนส่ง
* **ทางแก้:** ส่งออเดอร์เข้า **SNS Topic ก้อนเดียว** จากนั้นให้ **SQS Queue ของแต่ละแผนก** มา Subscribe รับข้อความต่อ
* **ข้อดี:** ทุกแผนกทำงานคู่ขนานกันได้อิสระ ถ้าแผนกออกใบเสร็จพัง แผนกตัดสต็อกและขนส่งก็ยังทำงานต่อไปได้ตามปกติ

## 3. Amazon EventBridge (นายสถานีไปรษณีย์อัจฉริยะ)

Amazon EventBridge พัฒนาต่อยอดมาจาก CloudWatch Events ทำหน้าที่เป็น **สมองส่วนกลางในการดักจับเหตุการณ์ (Event Bus)**

### EventBridge ต่างจาก SNS อย่างไร?
* **SNS:** กระจายข้อความแบบง่ายๆ (ส่งข้อความดิบไปหาผู้รับทุกคน)
* **EventBridge:** **ฉลาดกว่ามาก** สามารถแอบเปิดดูเนื้อหาในข้อความ (JSON Payload) แล้วคัดกรองได้ เช่น:
  * *"ถ้าออเดอร์มียอดเงินเกิน 100,000 บาท ให้ส่งไปหาผู้จัดการ"*
  * *"ถ้าเป็นออเดอร์ธรรมดา ให้ส่งไปเข้าคิวปกติ"*
* เชื่อมต่อกับระบบภายนอก (Third-party SaaS) ได้โดยตรง เช่น เมื่อมี Ticket เปิดใน **Zendesk** หรือ Alert จาก **Datadog** สามารถยิงเข้า EventBridge เพื่อสั่งให้ AWS Lambda ทำงานได้ทันที

## 4. Amazon Kinesis (ระบบสตรีมมิ่งข้อมูลความเร็วสูง)

เมื่อข้อมูลไม่ได้มาเป็นก้อนๆ แต่มาเป็น **"สายน้ำที่ไหลเชี่ยวตลอดเวลา" (Real-time Streaming Data)** เช่น สัญญาณ GPS รถบรรทุก 10,000 คันส่งพิกัดทุกๆ 1 วินาที, ข้อมูลการคลิกดูสินค้าของคนทั้งประเทศ, หรือ Log ระบบขนาดใหญ่

```
                                                ┌──> Kinesis Data Streams ──> [ Real-time Analytics ]
                                                │    (วิเคราะห์สดๆ วินาทีต่อวินาที)
[ ข้อมูล GPS / IoT / Logs ไหลต่อเนื่อง ] ───────┤
                                                │
                                                └──> Kinesis Data Firehose ──> [ S3 / Redshift ]
                                                     (พักข้อมูลเป็นชุด แล้วเทลงฐานข้อมูลอัตโนมัติ)
```

### ตารางเปรียบเทียบ Kinesis Data Streams vs Kinesis Data Firehose

| หัวข้อ | Kinesis Data Streams | Kinesis Data Firehose |
|---|---|---|
| **ความเร็วในการรับส่ง** | **Real-time แท้จริง (Latency ต่ำกว่า 200ms)** | **Near Real-time** (ต้องรอพักข้อมูลตาม Buffer เวลา 60-900 วินาที หรือ Buffer ขนาด 1-128 MB) |
| **การจัดการระบบ** | **Provisioned (กำหนดจำนวน Shards เอง)** หรือ On-Demand | **Serverless 100%** จัดการขนาดและขยายตัวให้อัตโนมัติ |
| **การเก็บรักษาข้อมูล** | เก็บข้อมูลไว้ในสตรีมได้ **1 ถึง 365 วัน** (เปิดให้ระบบอื่นย้อนกลับมาอ่านซ้ำได้) | **ไม่เก็บข้อมูล** (ทำหน้าที่แค่ดูดข้อมูล แล้วแปลงไฟล์ เทลงปลายทางทันที) |
| **ปลายทางยอดนิยม** | ส่งต่อให้ EC2, Lambda, หรือ Kinesis Data Analytics ประมวลผลสด | เทไฟล์ลง **Amazon S3, Amazon Redshift, OpenSearch, หรือ Splunk** |

## 5. Exam Trap & Keyword Decision Matrix

| โจทย์ระบุคีย์เวิร์ด (Exam Trigger) | ตัดสินใจเลือกใช้ (Architecture Decision) | เหตุผลและจุดหลอก |
|---|---|---|
| *"Decouple components, handle sudden traffic spikes without losing messages"* | **Amazon SQS (Standard Queue)** | คีย์เวิร์ดคือ "Decouple" และป้องกันระบบล่มเวลามีทราฟฟิกทะลัก |
| *"Messages must be processed strictly in order, exactly once, no duplicates"* | **Amazon SQS FIFO Queue** | คีย์เวิร์ดคือ "Strictly in order" และ "Exactly-once" ชี้เป้าไปที่ FIFO เสมอ |
| *"One message needs to be delivered to multiple microservices asynchronously"* | **SNS Fanout Pattern to multiple SQS Queues** | ส่งข้อความ 1 ชิ้น กระจายให้หลายระบบคู่ขนาน ตอบคู่ SNS + SQS |
| *"Scale EC2 worker instances based on the volume of incoming workload in SQueue"* | **Metric: ApproximateNumberOfMessagesVisible** | ห้ามเลือก CPU Utilization เด็ดขาด เพราะตัววัดที่ถูกต้องคือจำนวนข้อความในคิว |
| *"Capture real-time streaming data, load into S3 or Redshift with zero coding/management"* | **Amazon Kinesis Data Firehose** | ส่งข้อมูลสตรีมมิ่งลง S3/Redshift แบบอัตโนมัติ ไม่ต้องเขียนโค้ด ใช้ Firehose เสมอ |
| *"Filter events based on JSON payload content from third-party SaaS partners"* | **Amazon EventBridge** | กรองข้อความตามเนื้อหา JSON หรือเชื่อมต่อกับ SaaS ภายนอก ตอบ EventBridge |
